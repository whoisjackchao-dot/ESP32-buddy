# ADR-2026-10-16-02：设备 WiFi 的角色

> 状态：**草案（待用户批准）** —— 本文件是 **ADR 草案**，不是已批准决策，也不是已实现说明。
> 关联：`Q14`、`Q16`、`Q17`、`M4`、`M8`、缺口 `B11`/`B12`
> 背景：用户已批 `Q14`（时间源用 WiFi/NTP）与 `Q16`（设备需要 WiFi），但 **WiFi 的用途范围与 BLE 去留未定**。

## 1. 问题

设备同时有 **BLE**（旧项目既有链路）与 **WiFi**（新增）。WiFi 到底用来做什么？BLE 是否保留？

## 2. 证据

| 等级 | 内容 |
| --- | --- |
| 已批准 | `Q13` 事件入口放**主机层**；`Q14` 时间源用 WiFi/NTP；`Q16` 设备需要 WiFi |
| 文档级 | 上游设备具备 WiFi + Relay（`ADR-0012`：Relay 是**闭源 Cloudflare 服务 + 配对**）；WiFi 让设备"不插线也能连到它" |
| 本项目 | 旧项目设备↔主机走 **BLE（S3P）**；主机是 Windows |
| 本项目 | 缺口 `B11`（配网流程未定）、`B12`（BLE+WiFi 共存功耗，电池 250mAh） |

## 3. 候选方案

| 方案 | WiFi 用途 | BLE | 优点 | 代价 |
| --- | --- | --- | --- | --- |
| **A** | **仅授时（NTP）** | **保留** | 改动最小；M1–M5 完全不受影响 | WiFi 只对时略显浪费 |
| **B** | **也做设备↔主机传输** | 保留 | 摆脱"必须在主机旁" | 需配网 + socket 服务；BLE 冗余 |
| **C** | **也做设备↔主机传输** | 去掉 | 架构单一 | 推翻旧项目链路；配网成为唯一入口 |
| **D** | **也做 Relay（云中转）** | 视情况 | 主机不在旁边也能连 | 最重；引入云依赖与配对安全 |

## 4. 选定 / 未选定

- **选定**：**暂缺**（待用户批准）。
- **推荐**：**A**（先只授时 + 保留 BLE），把 B/C/D 作为**后续增量**。
- **未选定**：B、C、D 保留本条比较记录。
- **切换规则**：若 A 的 NTP 授时不可靠或 WiFi 常驻功耗不可接受（`B12`），应**重新提交设计选择**，**不自动切换到 B/C/D**；也不得在未批准时偷偷为 WiFi 分配传输职责。

## 6. 边界（批准后仍不覆盖）

- 不覆盖**配网方式**（`B11` 仍未定：无 App 能否配网？）。
- 不覆盖**功耗/续航**承诺（`B12`；不承诺续航数字）。
- 不覆盖 Relay 的**安全模型**（若将来走 D，须另开 ADR）。
- 本 ADR **不改变** `Q13`（事件入口仍在主机层）。
